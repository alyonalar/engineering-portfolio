# Log analysis

Источник: [`sanitized-log-sample.log`](sanitized-log-sample.log).

## Краткий вывод

По фрагменту можно восстановить один последовательный сценарий: приложение запустилось, пользователь загрузил документ с 19 вопросами, ответил на два вопроса и завершил квиз. Затем другой формат файла был отклонён, а Telegram polling получил сетевую ошибку.

Основной сценарий в этом фрагменте завершился без необработанного исключения. При этом логирование стоит доработать: пользовательская ошибка записывается как `WARNING`, в лог попадает правильный ответ, а для связи событий нет отдельного `session_id`.

## Проверка согласованности данных

Лог завершения содержит:

```log
Quiz finished for user A: solved=2, correct=1, wrong=1
```

Значения согласованы: `correct + wrong = solved`. Перед завершением действительно записаны ровно два ответа — один правильный и один неправильный.

Для документа также согласуются три события:

```log
Parsing finished successfully, total questions: 19
User A file parsed successfully, questions count: 19
User A questions inserted into database: 19
```

По этому фрагменту расхождения между количеством распознанных и сохранённых вопросов нет. Однако лог не доказывает отсутствие дублей в базе — для этого нужен запрос к данным или интеграционный тест.

## Наблюдения по уровням логирования

### Неправильный ответ записан как `WARNING`

Неправильный ответ — ожидаемое действие пользователя, а не нарушение работы системы. Если таких событий много, они создают шум среди действительно важных предупреждений. Для самого ответа достаточно `INFO`; `WARNING` стоит оставить для неожиданного состояния очереди или несогласованных данных.

### Неподдерживаемый формат записан как `WARNING`

Это допустимо, если команда отслеживает частоту некорректных загрузок. Если событие ожидаемое и бот корректно отвечает пользователю, уровень `INFO` также может быть достаточным. Решение зависит от принятой политики логирования.

### Сетевая ошибка требует продолжения события

```log
Failed to fetch updates - TelegramNetworkError: ... Server disconnected
```

Причина относится к соединению с Telegram, но по одной строке нельзя подтвердить автоматическое восстановление. После retry полезно писать отдельное событие: номер попытки, длительность паузы и факт успешного восстановления polling.

## Риски и рекомендации

1. **Не логировать правильный ответ.** Запись `correct=B` раскрывает часть содержимого теста. Достаточно `question_id`, результата и номера шага.
2. **Не сохранять исходное имя файла без необходимости.** Оно может содержать имя человека или другую персональную информацию. Для диагностики можно использовать внутренний `file_id`.
3. **Добавить `session_id`.** Один `user_id` не позволяет удобно разделить несколько последовательных квизов пользователя.
4. **Использовать структурированные поля.** `event=quiz_finished session_id=... solved=2 correct=1 wrong=1` проще искать и агрегировать, чем свободный текст.
5. **Логировать recovery после сетевого сбоя.** Иначе невозможно определить длительность недоступности по одному application log.
6. **Зафиксировать удаление временного файла.** В примере видна загрузка в `uploads`, но нет события cleanup.

## Границы анализа

Этот фрагмент подтверждает только показанную последовательность событий. Он не позволяет сделать вывод о параллельных пользователях, повторных callback, транзакционности записи в базу или восстановлении после разрыва соединения.
